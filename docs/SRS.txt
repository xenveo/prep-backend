1. Introduction
1.1 Purpose
This SRS defines the requirements for an invite-only web app that prepares candidates
for interviews for admin-approved job roles. Candidates study flash cards, then complete
a voice-enabled AI mock interview that gives feedback after every answer, re-asks the
question to check learning, and ends with a preparedness score.
The document is written for the product owner, developers, QA and anyone building or
evaluating the first release.
1.2 Scope
The product, referred to here as PrepPilot (working name), covers:
Invite-only access with email-based login
Admin management of users, job roles, flash cards and question banks
A flash-card study step per job role
An AI interviewer that asks questions by voice and text, evaluates answers, gives
written and spoken feedback, and re-asks each question once
Per-question and per-session preparedness scoring, with a results report

2. Overall description
2.1 Product perspective
PrepPilot is a new, standalone web app. It relies on three external services: an LLM API for
interviewing and evaluation, a speech service for STT and TTS, and an email service for
invites and login links. No integration with an ATS or HR system is required in release 1.

3. User journeys
3.1 Candidate journey
The coaching loop (ask, answer, feedback, re-ask, compare) runs once per question, 5
times by default, before the session is scored.
3.2 Admin journey
1. Log in and create a job role with description, seniority and key skills.
2. Add flash cards and questions with rubrics, or generate drafts with AI and edit them.
3. Preview the role and run a test interview.
4. Approve the role so it becomes visible to assigned candidates.
5. Invite candidates by email or CSV and assign them to the role.
6. Monitor progress and scores; open sessions to review transcripts and feedback.
7. Refine cards, questions and rubrics based on where candidates struggle.

5. Preparedness scoring model
The preparedness score weights the improved answer most, because the goal is to move
each candidate from low to high preparedness, and adds credit for learning between
attempts. The first answer still counts a little, as an honest baseline. All weights below are
defaults that admins can tune per role.
5.1 Attempt dimensions
The evaluator rates each attempt on four dimensions using a 1 to 5 anchored rubric,
mapped to 0, 25, 50, 75 and 100.
5.2 Learning score
For each retry, the evaluator lists the improvement points from the first feedback and
marks each as applied, partly applied or not applied (1, 0.5, 0). The learning score for that
question is the share applied, from 0 to 100. A skipped retry scores 0.
5.3 Session score
\text{Preparedness} = 0.20\,\overline{A_1} + 0.55\,\overline{A_2} + 
0.25\,\overline{L}

5.4 Readiness bands
5.5 Scoring reliability
The evaluator shall return structured JSON (scores, evidence quotes from the answer,
feedback text) validated against a schema; invalid output is retried once.
Each score shall cite evidence from the transcript so admins can audit it.
Evaluation runs at low temperature for consistency. Before launch, scores on a set of at
least 30 sample answers per role should be compared with a human reviewer's, aiming
for agreement within one rubric level on 80% of answers.
5.6 Progress across sessions
Because the aim is growth, the candidate's dashboard and results page shall show their
first-session score as a baseline, their latest score, and the change between them, plus
band movement (e.g. Developing to Nearly ready). Admins see the same baseline-to-
latest change per candidate and per role.

The interview room shows the AI interviewer (avatar or waveform), the current question, a
record or type control, a timer, the transcript, and a feedback panel that expands after
each answer. Every spoken output also appears as text, so the flow works with sound off.
7.2 AI interface (LLM)
Three prompt roles, each versioned in config rather than code:
1. Interviewer: given the role, question and conversation so far, produces the spoken
question, transitions and the retry prompt.
2. Evaluator: given the question, rubric, transcript and (for retries) the first feedback,
returns JSON with dimension scores, evidence, what was right, what was missing,
delivery notes, improvement points and a spoken summary.
3. Session summariser: given all attempts, returns strengths, focus areas and the band
message.
The LLM provider shall sit behind an internal adapter so the model can be changed
without app changes.
7.3 Speech interface
STT: streaming or batch transcription with word timestamps (needed for pace and
filler-word metrics).
TTS: a natural voice for questions and feedback; audio is cached per question to cut
cost and latency.
7.4 Email interface
Transactional email (e.g. Amazon SES, SendGrid or Postmark) for invites, login codes and
optional session-complete notices. Emails must include SPF/DKIM setup to avoid spam
folders.

9. Suggested architecture and tech stack
A single web backend with four modules is enough for release 1; the interview engine is
the core, and every AI, speech and email provider sits behind an adapter.
9.1 One answer, end to end
1. The browser records the answer (MediaRecorder) and uploads it, or sends typed text.
2. The speech service returns a transcript with word timestamps; the engine computes
pace and filler-word count.
3. The scoring engine sends question, rubric and transcript to the LLM evaluator and
validates the JSON it returns.
4. The attempt is saved; TTS turns the feedback summary into audio.
5. The candidate sees and hears the feedback; the engine then re-asks the question or
moves on.

10.3 Acceptance criteria (release 1)
1. An invited user logs in with an email code; an uninvited email cannot.
2. A candidate sees only approved, assigned roles.
3. A candidate completes all flash cards and starts the interview.
4. For each question, the candidate answers by voice or text and receives written and
spoken feedback covering content and delivery.
5. The same question is re-asked, re-evaluated, and a first vs retry comparison is shown.
6. The session ends with a 0 to 100 score, a band, strengths and focus areas that match
section 5.
7. An admin can invite users, publish a role with cards and questions, and view every
candidate's results.
8. Feedback is returned within 8 s at p90 across 100 test sessions.
